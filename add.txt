1.Build a robust client-side “System State Detection and Handling” module for a web application deployed on a platform with cold starts (e.g., server sleeps after inactivity).



The system must correctly detect and differentiate between:



1. User is offline (no network)

2. User has network but no internet access

3. Server is sleeping (cold start)

4. Server is waking (slow response / high latency)

5. Server is fully awake

6. Server error (5xx responses)

7. Resource not found (404 - must remain unchanged and separate)



Core Requirements:



1. Do NOT use HTTP 404 page for server state handling.

   

   - 404 must only represent "resource not found".

   - Server state must be handled via a separate UI layer or route (e.g., /system-status).



2. Implement a lightweight backend endpoint:

   GET /health

   

   - Returns 200 OK immediately when server is awake

   - Must NOT include database calls or heavy logic

   - Response example:

     { "status": "ok", "timestamp": <number> }



3. Client-Side Detection Logic:

   

   - Step 1: Check browser network status using navigator.onLine

     → if false → state = "offline"

   - Step 2: Perform external internet check (lightweight request)

     → if fails → state = "network_issue"

   - Step 3: Attempt API request with timeout (5–8 seconds)

     → if timeout occurs → mark as "possible_cold_start"

   - Step 4: Start background polling of /health every 2–3 seconds

     → if /health responds slowly (>8s) → state = "waking"

     → if /health responds quickly → state = "awake"

     → if repeated failures → state = "sleeping"



4. State Definitions:

   

   - "offline" → no network connection

   - "network_issue" → connected but internet unreliable

   - "sleeping" → server not responding to repeated probes

   - "waking" → server responding but with high latency

   - "awake" → server responding normally

   - "error" → backend returned 5xx

   - "not_found" → true 404 (must not be overridden)



5. UI Behavior:

   

   - Do NOT navigate away from current route unnecessarily

   - Show a global overlay or fallback screen instead
   - use animation based on event like sleep-zzzzz, walking - !!!!(attractive ui).

   

   UI messages:

   

   - offline → "You are offline. Check your connection."

   - network_issue → "Your connection is unstable."

   - sleeping → "Server is starting. This may take up to 30 seconds."

   - waking → "Server is waking up… almost ready."

   - error → "Something went wrong on our side."

   - not_found → existing 404 page (unchanged)



6. Retry Strategy:

   

   - Automatically retry /health every 2–3 seconds while in sleeping/waking

   - Once server becomes "awake", retry the original failed request

   - Provide manual "Retry" button for network_issue and error states



7. Performance Constraints:

   

   - Do not run detection on every page load

   - Trigger detection only when:

     a) Initial critical request fails

     b) Socket connection fails

   - Avoid excessive polling



8. Socket Handling:

   

   - On socket connection failure:

     → trigger system state detection

     → retry connection after server becomes "awake"



9. Code Architecture:

   

   - Centralize logic in a reusable hook or service (e.g., useSystemState)

   - Avoid duplicating logic across components

   - Ensure idempotent retries and no infinite loops



10. UX Principle:



- Do not claim certainty (e.g., avoid “Server is sleeping” as absolute truth)

- Use probabilistic messaging like:

  “Server is starting…” or “Taking longer than usual…”



Goal:

Deliver a clean, maintainable system that provides accurate user feedback, avoids false assumptions, and gracefully handles cold starts without misusing HTTP semantics.
